03

Token Agent y conectividad — superado con wget

Tu HTTP 403 dentro de zammad-snipeit-zammad-nginx-1 era esperable: ese contenedor no tiene ZAMMAD_TOKEN. Verificado 200 OK desde n8n con wget.
N8N / HOSTdocs/05 §5.3–§5.4
Diagnóstico: ejecutaste la prueba dentro de zammad-nginx, donde la variable está vacía. El header probablemente viajó como Authorization: Token token= → HTTP 403. Además usaste localhost:8080 dentro del contenedor; desde n8n/host la ruta correcta es zammad-nginx:8080 o localhost:8000 respectivamente. Ojo: el contenedor n8n no trae curl, usa wget.
docker compose exec -T n8n sh -lc '
printf "SNIPE_HOST=%s\nZAMMAD_HOST=%s\n" "$SNIPE_HOST" "$ZAMMAD_HOST"
if test -n "$ZAMMAD_TOKEN"; then echo "ZAMMAD_TOKEN=present"; else echo "ZAMMAD_TOKEN=VACIO"; fi
command -v curl || echo "curl: no encontrado (normal en n8n)"
command -v wget || echo "wget: no encontrado"
'
Esperado:
SNIPE_HOST=http://snipe-it:80
ZAMMAD_HOST=http://zammad-nginx:8080
ZAMMAD_TOKEN=present + wget disponible.
docker compose exec -T n8n sh -lc '
test -n "$ZAMMAD_TOKEN" || { printf "ZAMMAD_TOKEN vacio en n8n\n" >&2; exit 1; }
rm -f /tmp/zammad-check.json
wget -S -O /tmp/zammad-check.json \
  --header="Authorization: Token token=$ZAMMAD_TOKEN" \
  "http://zammad-nginx:8080/api/v1/users?limit=1" 2>&1 | head -20
echo "---EXIT:$?"
ls -l /tmp/zammad-check.json
head -c 500 /tmp/zammad-check.json; echo
'
Esperado: HTTP/1.1 200 OK y JSON válido. Si cambiaste envs/n8n.env, recrea n8n: docker compose up -d --force-recreate n8n.
Matiz importante: GET /users valida conectividad, pero el runtime usa PUT /tickets/{id}. Si el 403 persiste con token presente, el fallo real es permiso Agent sobre el grupo del ticket; se confirma en el paso 9 contra un ticket descartable.

Smoke test directo al webhook

Con el trigger aún desactivado. Aísla fallos de n8n frente a fallos de Zammad.
HOSTn8n Production URL
TICKET_ID=123
TICKET_NUMBER='100001'
EMAIL='usuario-prueba@example.local'

PAYLOAD=$(jq -n \
  --argjson id "$TICKET_ID" \
  --arg number "$TICKET_NUMBER" \
  --arg email "$EMAIL" \
  '{ticket_id:$id,ticket_number:$number,customer_email:$email}')

curl -sS \
  -o /tmp/zammad-enrich-response.json \
  -w 'HTTP %{http_code}\n' \
  -X POST \
  -H 'Content-Type: application/json' \
  --data "$PAYLOAD" \
  'http://localhost:5678/webhook/zammad-ticket-created'

jq . /tmp/zammad-enrich-response.json
Esperado: {"ok": true, "ticket_id": 123, "ticket_number": "100001", "log_status": "ok"}. Si recibes ok:false, no sigas: revisa la ejecución en n8n y el paso 3.

Verificar ticket + auditoría

El éxito real es el PUT reflejado en Zammad y en Postgres.
ZAMMAD UIPOSTGRES n8n
En el ticket: snipe_asset_count con el número real, tags separados por coma, summary con bloque ACTIVOS SNIPE-IT (N) + -------------------- + NN modelo/ tag/ estado/ S/N serial (4 líneas por activo, orden asset_tag, datos reales Snipe-IT sin conversión) y artículo interno con el mismo bloque.
SELECT id, created_at, workflow_name, execution_id,
  entity_id, entity_tag, operation, response_status, error_message
FROM public.integration_sync_log
WHERE source_system = 'zammad'
  AND entity = 'ticket'
  AND operation = 'enrich_assets'
ORDER BY id DESC
LIMIT 5;
Esperado: fila nueva con operation=enrich_assets, response_status=200 y error_message vacío.
